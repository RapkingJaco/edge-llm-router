## 📖 名詞小抄（看不懂英文詞先查這）

| 詞 | 白話意思 |
|---|---|
| **token** | 文字的一小塊（≈一個詞/詞片段；1 token ≈ 1~2 個中文字）。LLM 以 token 為單位處理與生成 |
| **請求 request** | 一個 LLM 查詢；程式裡只看它多大（input/output token 數）。模擬時是**自動生成的合成請求**，不是誰打字打進來的 |
| **節點 node** | 一個「執行請求的地點」：本機/邊緣/雲。**平常是模擬出來的三組參數，不是三台真機器** |
| **TTFT** | time-to-first-token，**首字延遲**：按送出到看到第一個字的時間。體感關鍵指標 |
| **prefill** | LLM **讀完你整段輸入、吐出第一個字**的階段；時間 ∝ 輸入 token 數 → 決定 TTFT |
| **decode** | 第一個字之後，**一個 token 一個 token 把答案吐完**的階段；時間 ∝ 輸出 token 數 |
| **wait（排隊等待）** | 窗口都滿、請求在隊伍裡**乾等**的時間（還沒開始處理） |
| **service（處理時間）** | 請求真正佔住一個窗口的時間 = prefill + decode |
| **capacity** | 一個節點有幾個**平行服務窗口**（本機 2 / 邊緣 4 / 雲 16） |
| **RTT** | round-trip time，網路來回時間 |
| **丟棄 drop** | 排隊等太久（>4000ms）就拒收該請求 |
| **episode（一局）** | 一整段模擬（≈60 秒、約 500 個請求）；RL 一局一局地玩來學 |
| **observation（觀測）** | agent 每步看到的狀態（這裡 15 維數字） |
| **action（動作）** | agent 的決策；這裡是三選一（本機/邊緣/雲） |
| **reward（獎勵）** | 每步好壞分數；這裡越接近 0 越好 |
| **w（權重）** | 你多在乎「快」vs「省」的偏好；w_lat + w_cost = 1 |
| **MDP** | 馬可夫決策過程：一連串「看狀態→做動作→拿分→進下一狀態」的序列決策問題 |
| **PPO** | 一種主流 RL 演算法（會自己學的玩家） |
| **GAE** | 估「這動作比平常好多少（Advantage）」的方法，用旋鈕 λ 平衡穩定 vs 準確 |
| **Critic / 價值函數** | 估「這個狀態前景多好」的分數 |
| **baseline 基準線** | 傳統寫死策略（greedy/輪詢/全雲/全本機），拿來對照證明 AI 贏 |
| **Sim-to-Real** | 在模擬裡訓練、拿真硬體量測校準，讓模擬像真實 |
| **Domain Randomization (DR)** | 訓練時在真值附近隨機化參數，讓策略對「真實有落差」也穩 |
| **Pareto 前緣** | 「成本 vs TTFT」的最佳權衡曲線；一個權重條件化 policy 可掃出整條 |

## 0. 一句話 + 大圖

**你做的是一個聰明的「帶位員」。**

想像超忙餐廳：客人不停湧入（= 一個個 AI 請求），門口帶位員（= 你的 RL agent）要決定**每個客人帶去哪張桌子**（= 本機/邊緣/雲三個處理地點）。帶得好 → 又快又順又省；帶不好 → 有人乾等、桌子被擠爆。

**你不是在做 AI 問題的「答案」（那是廚房的事），你做的是「誰去哪」的決策大腦。** 這在業界叫 **LLM 推論路由 / 排程（LLM serving / inference routing）**。

🧠 記憶鉤：**你的專案 = LLM 界的 Uber 派單。**

## 1. 三張桌子：本機 / 邊緣 / 雲端

### 各是什麼（物理比喻）

| 桌子 | 是什麼 | 比喻 |
|---|---|---|
| **本機 local** | 使用者身邊的弱裝置（手機） | **2 個爐子的路邊攤**：免費，但人一多就大排長龍、等到受不了的客人直接走 |
| **邊緣 edge** | 附近的中型 GPU 盒（你的 4070 桌機） | **中型餐館**：中間值 |
| **雲端 cloud** | 遠方的大型資料中心（Gemini） | **16 個爐子的大飯店**：又快又穩，但收費是路邊攤的 100 倍 |

### 三者差異 = 5 個數字（都在 `configs/default.yaml`）

| 參數 | 白話 | 本機 | 邊緣 | 雲端 |
|---|---|---|---|---|
| `rtt_ms` | 網路來回 | **2**（在身邊） | 8 | **120**（很遠） |
| `prefill_ms_per_token` | 讀輸入多慢 | 6.0 | 1.5 | **0.4** |
| `decode_ms_per_token` | 吐字多慢 | **25**（慢） | 8 | **3** |
| `capacity` | 同時幾個服務槽 | **2**（一擠就爆） | 4 | **16** |
| `cost_per_request` | 每次標價 | **0.0001** | 0.001 | **0.01**（貴 100×） |

### 為什麼一定要分三段？（這是專案的靈魂）

因為三者各有**明確的優劣取捨**，沒有「一律最好」的選項：

- **本機**：網路最近、超便宜，但算得慢、**一擠就爆**。
- **雲端**：算最快、容量大到擠不爆，但**網路遠又貴 100 倍**。
- **邊緣**：兩者中間，緩衝。

閒的時候用便宜的本機/邊緣最划算；一忙、便宜節點快爆了，就得放一些去貴的雲端保速度。**「什麼時候該花錢買速度」正是 RL 要學的**。

⚠️ 關鍵：**如果節點速度固定不變，最佳解永遠是「全丟最快的」，RL 就沒得學、專案不成立。** 所以我們做了「**忙 → 變慢 → 塞爆丟棄**」的排隊模型，製造取捨張力。

### 這三個節點在哪裡？（重要：平常不是三台真機器）

平常（訓練 + 網頁 demo）三個節點都是**同一個 Python 程式裡「假裝」的三組參數 + 排隊公式**，全在你電腦 CPU 上算——沒有真手機、沒真跑顯卡、沒真打雲端。

```
你的一台電腦（CPU 跑一個 Python 程式）
 └─ 程式裡假裝有三個節點（三組參數 + 排隊公式）
      ├ 本機 local ← 永遠假裝（模擬弱手機）
      ├ 邊緣 edge  ← 平常假裝；開 Ollama 時 → 真的送你 4070 顯卡
      └ 雲端 cloud ← 平常假裝；設了 Gemini key 時 → 真打 Google 伺服器
```

| 常見誤會 | 正解 |
|---|---|
| 本機 = 我的 CPU？ | ❌ 本機是**模擬的弱手機**（純公式），不是真在跑推論 |
| 邊緣 = 顯卡？ | 🟡 **只有開 Ollama 時**，邊緣才 = 你 4070 顯卡真跑 llama3.2 |
| 雲端在哪？ | 🟡 概念上是 Google Gemini 伺服器；**只有設了 key** 才真打 |

（對照碩論：你論文訓練時 Quest2/PC 也是在模擬裡跑、最後才校準到真機。這裡一樣。）

### 什麼是「一個請求 request」

一個請求 = 一個 LLM 查詢，程式裡只有三個欄位：`input_tokens`（輸入多長）、`output_tokens`（會生成多長）、`prompt_text`（實際文字，只有真打時才用）。**模擬時請求是自動生成的合成工作（每局約 500 個、長短隨機），不是誰打字進來的**；對 RL 來說主要就看「多大」。
（⚠️ 網頁右邊你打的中文是「改 w 的方針指令」，**不是**請求。）

### 排隊模型：實際走一遍（wait vs service）

每個節點有 `capacity` 個平行窗口，用 `_free_at[]` 記各窗口何時空出。請求進來：挑最早空的窗口，`wait = max(0, 該窗口空出時間 − 現在)`；若 `wait > 4000ms` → 丟棄；否則佔窗口 `service` 毫秒。

本機（2 窗口，假設每個 service = 2000ms）走一遍：

| 時間 | 事件 | wait |
|---|---|---|
| t=0 | A 來 | 0（窗口1 空） |
| t=10 | B 來 | 0（窗口2 空） |
| t=20 | C 來 | 兩窗口忙到 2000/2010 → 等到 2000 → **wait = 2000−20 = 1980ms** |

**wait（排隊乾等、還沒處理）≠ service（真正處理）**。C 的 1980ms 是純排隊。節點越忙 → wait 越大 → TTFT 越高。

### 兩條公式：TTFT vs service（含 prefill / decode）

```
TTFT    = wait + RTT + prefill        ← 只到「第一個字」，含 prefill、不含 decode
service = prefill + decode            ← 佔住窗口的總時間
prefill = prefill_ms_per_token × 輸入token
decode  = decode_ms_per_token  × 輸出token
```

- **prefill**：模型**讀完你的輸入、蹦出第一個字**（∝ 輸入長度）→ 決定 TTFT。
- **decode**：第一個字之後**一個 token 一個 token 吐完**（∝ 輸出長度）→ 不影響 TTFT，但**佔住窗口很久**、拖累後面請求的 wait。
- 例（送邊緣，輸入 100 / 輸出 200）：`prefill = 1.5×100 = 150ms`（→ 首字）、`decode = 8×200 = 1600ms`、`service = 1750ms`。

🧠 記憶鉤：三張桌子 = **路邊攤（本機）→ 中型餐館（邊緣）→ 大飯店（雲端）**；離你越近越便宜但越弱，越遠越強但越貴。這也正是**邊緣運算的 computation offloading**，接你碩論。

## 2. 我們量什麼（指標）

| 指標 | 白話 | 好的方向 |
|---|---|---|
| **TTFT** | 首字延遲：按送出→看到第一個字的時間。= 排隊等待 + 網路來回 + prefill（讀完你的輸入）| 越低越好（體感關鍵） |
| **成本 cost** | 每個請求的標價加總 | 越低越好 |
| **丟棄率 drop rate** | 塞爆、等太久被拒的請求比例 | 越低越好（0 最好） |
| **reward 綜合分** | 把上面三者合成一個分數（見下）| 越接近 0 越好 |
| **領先 % lead** | AI 比傳統策略好多少（demo 中面板那個數字） | 越高越好 |
| **gap** | Sim-to-Real：模擬預測 vs 真實量測的差距 | 越小 = 模擬越像真 |

**reward 怎麼合成**（核心公式）：
```
reward = -( w_lat · 正規化TTFT  +  w_cost · 正規化成本 )  -  丟棄懲罰
```
- 前面加負號：延遲/成本越低分數越接近 0（越好）。
- `w_lat / w_cost` = 你這局**多在乎快 vs 多在乎省**（兩者加起來 = 1）。
- 正規化：TTFT ÷ 2000ms（可接受上限）、成本 ÷ 全用雲端最貴情況，各壓到 0~1，`w` 才是乾淨的偏好旋鈕。
- 丟棄：大扣分，逼 agent 別把便宜節點塞死。

🧠 記憶鉤：**TTFT = 服務生多久來點餐**（體感關鍵）；**reward = 一張把「快、省、別塞爆」揉在一起、可調權重的成績單**。

## 3. 怎麼訓練 AI（從零）

### (a) RL 是什麼

一個 RL 環境就是一台**電動遊戲**，每一格（step）：
```
看畫面(observation) → 按按鈕(action) → 拿分數(reward) → 下一格畫面 …
```
agent 靠玩很多局、看哪種按法拿高分來學。這裡：

- **一步 = 一個請求**（每來一個請求就選一個節點送）。
- **一局(episode) ≈ 60 秒一波流量、約 500 個請求。**

### (b) 這個遊戲的三要素（MDP）

| 要素 | 這裡是什麼 |
|---|---|
| **看畫面 observation（15 維）** | 這個請求多大(2) + 三節點各自多忙(9) + 全域花多少錢/多塞(2) + 你現在在乎什麼 w(2) |
| **按按鈕 action** | `Discrete(3)`：本機 / 邊緣 / 雲，三選一 |
| **拿分數 reward** | 上面第 2 節那條公式 |

⚠️ **不洩上帝視角**：請求的「輸出會多長」只給 agent **帶雜訊的估計**，不給真值——因為真實世界你事先不知道它會生多長。讓 agent 偷看真值，模擬裡很強、接真機就破功。這是 Sim-to-Real 能成立的誠實前提。

### (c) PPO 是什麼（會自己學的玩家）

PPO 是一種 RL 演算法。快速回顧那條「撞牆補洞」的鏈：
1. 最原始：分數高的做法就多做 → 但**成績被運氣干擾（不穩）、又沒基準**。
2. 改看 **Advantage**「比平常好多少」→ 需要一個 **Critic（價值函數）**估「這局面前景分」。
3. 估 Advantage 要在「信真實結果 vs 信 Critic」間取捨 → **GAE 用旋鈕 λ 調到又穩又不歪**。
4. 想重用經驗又怕練壞 → **PPO 用 clip（牽狗繩）**限制單次更新幅度。

🧠 記憶鉤：**Critic = 西洋棋高手看一眼的局面前景分；GAE = 信眼睛還是信直覺的旋鈕；clip = 牽狗繩別暴衝。**

### (d) 權重條件化（招牌功能）

把偏好權重 `w` 也塞進 observation，**每局隨機抽一組 w** 來訓練 → 學成**一整族**策略 `π(動作|狀態, w)`。於是同一個網路，改 `w` 就換行為、**零重訓**。

🧠 記憶鉤：不是訓練「一個專才」，是訓練「**一個通才帶位員**」——你下什麼方針(w)，他立刻照那個方針帶。

### (e) 基準線（對照組，用來證明「AI 贏」）

寫死的傳統玩家：`greedy`（挑最快）、`round_robin`（輪流）、`all_cloud`、`all_local`。它們**都不看 w**，行為固定。

### (f) 結果（地板 → 天花板）

| | 丟棄率 | 成本 | reward | 說明 |
|---|---|---|---|---|
| 隨機亂丟（地板） | 40%+ | — | ~ -700 | 不看畫面硬塞爆 |
| greedy（最強傳統） | 0% | 5.11 | -284 | 穩，但**狂燒錢**（幾乎全丟雲） |
| **PPO（w=0.5）** | **0%** | **3.62** | **-211** 🏆 | 一樣穩，但**省 29%** |

**跨整條偏好光譜，PPO 每個 w 都贏**：w 要快贏 8% → 平衡贏 28% → **要省贏 39%**（越在乎成本贏越多，因為傳統策略只能站在一個固定點）。

**同一個網路、零重訓，只改 w 的行為變化**：
| 方針 | local | edge | cloud |
|---|---|---|---|
| 要快 (w_cost=0.1) | 0% | 18% | 82% |
| 要省 (w_cost=0.9) | 4% | 42% | 54% |

**怎麼跑訓練**：`uv run python scripts/train_wc.py`（CPU，幾分鐘，約 200k~500k 步）。

## 4. 模擬 vs 真實（Sim-to-Real）

- **環境本身是模擬**（排隊公式算的）；訓練、即時 demo 都跑**校準過的模擬**。
- **真實**的部分：①拿真硬體量測**校準**模擬（你 4070 真跑 Ollama llama3.2 量真 TTFT）；②可選的真 Gemini 抽驗。
- 真跑**只用於校準/抽驗**，不進訓練/即時主迴圈（真生成慢）。
- **成果**：模擬 vs 真實的 gap 從 **2286ms → ~44ms（↓98%）**（用 Wasserstein 分布距離量）。

🧠 記憶鉤：**在駕訓場（模擬）練，但駕訓場照真實路口（4070 量測）校準過，所以一上路不失準。** 這就是你碩論的方法論，換到 LLM serving。

⚠️ 面試誠實邊界：**別說「這是真的在跑的分散式服務系統」**。要說「這是**被真實硬體校準過的模擬器**，我在上面訓練 RL 並驗證 gap」。

## 5. 控制層：一句中文改行為（結構化輸出）

打「成本太高，多用本機」→ 轉成 `w=(延遲0.1, 成本0.9)` → 餵進 obs → PPO 當場改分流、**零重訓**。傳統策略無視 w，所以只有 AI 會變，對照更明顯。

**核心設計：只吐意圖、不讓 LLM 吐數字。** LLM/規則只判斷**意圖**（省成本/要快/平衡）+ 強度，再由確定性程式換算成 w。這是「絕不盲信 LLM」的安全網——看不懂就維持原方針。

🧠 記憶鉤：**w 是旋鈕，中文是「用講的轉旋鈕」，PPO 立刻照新旋鈕跑。**

## 7. 面試怎麼講（三賣點 + 一句話）
